# lark-card-designer 需求分析

更新日期：2026-06-30

## 1. 项目定位

`lark-card-designer` 是一个用于指导飞书/Lark 卡片样式决策的 Codex skill。

它的目标不是直接生成最终可发送的飞书卡片，也不是封装飞书 API，而是在用户给出数据、场景、意图或输出口径后，稳定判断应该采用什么卡片样式、信息层级、组件组合和视觉规则。

核心价值：

- 降低“提示词漂移”：用决策矩阵、组件规则、检查表替代自由发挥的提示词。
- 补足现有项目空白：现有 GitHub 仓库多是 sender、builder、renderer，本项目补“样式决策层”。
- 让不同数据类型有不同表达：报告、商品、销售、资讯、审批、复盘不套同一种卡片。
- 帮助下游生成器或开发者更稳定地做卡片：输出结构化建议，而非只给审美描述。

## 2. 已确认需求

### 2.1 Skill 名称

- 项目/skill 命名：`lark-card-designer`

### 2.2 核心用途

- 根据数据类型、数据意图、输出口径判断合适的飞书卡片样式。
- 主要用于指导不同输出口径的卡片样式。
- 不直接负责把卡片做出来。
- 不把“生成提示词”作为主要产物。

### 2.3 优先输出口径

用户已确认优先支持：

1. 管理层口径
2. 业务运营口径
3. 一线执行口径
4. 复盘分析口径
6. 知识/资讯口径

暂不优先支持：

- 群通知口径

### 2.4 已确认场景

数据层面：

- 日报
- 周报
- 商品数据
- 销售数据

信息集合层面：

- 前沿 blog 汇总
- 文章收集汇总
- 资讯/知识聚合

流程操作层面：

- 审批卡片

### 2.5 输出形态偏好

推荐作为 skill 的主要输出：

- 样式决策说明
- 信息架构大纲
- 组件建议
- 视觉规则
- 交互规则
- JSON 骨架示意
- 校验清单

不推荐作为主要输出：

- 纯提示词模板
- 完整可发送卡片 JSON
- 飞书 API 调用代码
- 通用审美建议

### 2.6 样例策略

已确认采用：

- 每类一个最小样例。

优先覆盖：

- 日报/周报样例
- 商品数据样例
- 销售数据样例
- 文章/资讯汇总样例
- 审批样例
- 复盘样例

样例应放在 references 中，不放进 `SKILL.md` 主体，避免 skill 触发时加载过重。

### 2.7 JSON 骨架边界

已确认采用：

- 给接近飞书 JSON 2.0 的骨架，但不保证可直接发送。

设计含义：

- JSON 骨架用于表达卡片结构、组件层级和关键字段占位。
- 不承担完整 API 参数、鉴权、回调、发送 envelope。
- 输出时必须标注这是结构示意，不是生产可发送 JSON。

### 2.8 图表能力边界

已确认采用：

- 说明趋势、占比、漏斗、排行分别适合什么图表。

设计含义：

- skill 需要判断“此处应该用图表还是表格/KPI/文字”。
- 对趋势、占比、漏斗、排行、目标达成、异常波动给出图表类型建议。
- 不默认输出完整图表 JSON。
- 图表建议应服务于卡片首屏理解，不为了装饰而使用。

### 2.9 审批/交互深度

已确认采用：

- 审批/交互卡片做到状态机建议。

设计含义：

- 至少覆盖待审批、已同意、已拒绝、已退回、已过期等状态。
- 对每个状态说明首屏重点、按钮状态、颜色语义和审计信息位置。
- 不做审批人、代理人、RBAC、权限系统等工程实现规则。
- 权限与审计只作为卡片信息字段和风险提示，不作为执行逻辑。

### 2.10 口径缺省处理

已确认采用 A+B 混合策略：

- 当数据类型、场景和读者意图较明显时，主动推断输出口径，并在输出中标注假设。
- 当口径会显著改变卡片结构，或审批/高风险/强执行场景信息不足时，先追问一个最关键问题。
- 推断时可给出 1 到 2 个替代口径，但不默认输出完整多口径版本。

设计含义：

- skill 不应频繁打断用户。
- skill 也不应在关键口径不明时强行生成。
- 追问要短，只问能改变卡片结构的关键变量。

### 2.11 输出格式结构化程度

已确认采用：

- Markdown + 结构化决策块。

设计含义：

- 先用简短自然语言说明关键判断。
- 再输出固定字段块，便于下游实现者或生成器稳定提取。
- 固定字段至少包括 `card_intent`、`card_pattern`、`information_architecture`、`component_plan`、`visual_rules`、`interaction_rules`、`json_skeleton`、`validation_checklist`。
- 不使用纯 JSON/YAML 作为默认回答格式。

### 2.12 主触发场景

已确认主场景：

- 开发过程中，只要涉及飞书/Lark 卡片的样式、结构、组件、信息层级、交互或视觉状态设计，就应调用 `lark-card-designer`。

这意味着 skill 的触发描述应覆盖：

- 为新功能设计飞书卡片
- 为已有数据输出选择飞书卡片样式
- 为不同输出口径设计卡片信息架构
- 评估或优化已有飞书卡片设计
- 将业务数据、审批流程、日报周报、资讯汇总转化为卡片设计方案

触发描述不应把它写成：

- 直接发送飞书消息
- 调用飞书 API
- 生成完整可发送 JSON
- 普通 Markdown 美化

### 2.13 已有卡片评审/优化范围

已确认采用：

- 设计新卡片 + 评审/优化已有卡片。

设计含义：

- skill 可以用于新功能的卡片设计。
- skill 也可以用于已有卡片的可读性、信息层级、组件选择、视觉状态、交互状态评审。
- 评审输出应以问题、风险、改进建议和可选结构骨架为主。
- 不默认承担旧 JSON 到新 JSON 的自动迁移。

### 2.14 开发实现参与边界

已确认采用 A + 指导/评审：

- 角色是飞书卡片设计师。
- 输出设计决策、信息架构、组件建议、视觉规则、交互状态和检查表。
- 可以阅读已有代码、JSON、模板或截图，评审其是否符合设计目标。
- 可以指出实现偏差、风险和修改方向。
- 不直接参与代码、JSON、模板实现修改。

设计含义：

- skill 的主职责是设计判断和设计评审。
- 当开发任务需要修改文件时，其他开发能力可以执行修改；本 skill 提供设计依据。
- 输出措辞应保持“建议/评审/设计规范”口吻，不伪装成实现工具。

### 2.15 飞书能力基准

已确认采用：

- JSON 2.0 为主 + CardKit 概念参考。

设计含义：

- 默认按飞书卡片 JSON 2.0 的组件能力进行结构设计。
- JSON 骨架使用接近 JSON 2.0 的组件层级表达，但不保证可直接发送。
- 当设计涉及局部更新、流式更新、模板管理、卡片实体生命周期时，参考 CardKit 的概念。
- JSON 1.0 仅作为评审旧卡片或兼容说明时提及，不作为新设计默认基准。

### 2.16 视觉风格边界

已确认采用轻量 B：

- 默认克制，语义状态优先。
- 可以给 header、标签、关键数字、风险项的强调色建议。
- 不做复杂品牌定制选型。
- 不默认输出强主题化风格。

设计含义：

- 强调色只用于表达状态、风险、优先级、关键指标或行动焦点。
- 视觉建议应服务于清晰度，不服务于装饰。
- 如果用户明确提供品牌规范，可以参考，但不把品牌定制作为默认流程。

### 2.17 质量验收严格度

已确认采用：

- 设计红线 + 改进建议。

设计含义：

- 新卡片设计输出需要附带自检清单。
- 已有卡片评审需要指出设计红线、风险和修改方向。
- 检查范围包括首屏清晰度、信息层级、组件选择、交互状态、状态色语义、数据来源、移动端可读性。
- 不默认使用复杂评分量表。
- 只有用户明确要求评估分数时，才输出评分。

### 2.18 标准 skill 交付

已确认：

- 按 Codex 标准 skill 交付。

交付结构：

- `SKILL.md`：必需，作为 skill 入口，包含触发描述和核心工作流。
- `agents/openai.yaml`：推荐，提供 UI 展示元数据和默认提示。
- `references/`：必需，存放决策矩阵、口径说明、卡片模式、组件规则、视觉规则和约束。

交付边界：

- 不在最终 skill 包中创建 README、安装指南、更新日志等额外说明文件。
- 不把调研过程文档作为 skill 默认加载内容。
- 当前 `docs/` 目录作为项目调研和原始资料留存；真正运行时知识应沉淀到 `references/`。
- 不需要 `scripts/`，除非后续出现必须用代码保证稳定性的重复任务。
- 不需要 `assets/`，除非后续有固定模板、图片或品牌资源。

### 2.19 跨 Coding CLI 兼容

已确认：

- 交付物需要尽量让主流 coding CLI 都能使用，包括 Codex、Claude Code、OpenCode 等。

设计原则：

- 以通用 Agent Skill 形态作为核心：`SKILL.md` + `references/`。
- 核心知识只维护一份，不为不同 CLI 复制多套规则。
- `SKILL.md` 内避免 Codex 桌面专有指令、工具名、UI 指令和本地绝对路径。
- references 使用普通 Markdown 和相对链接，保证在不同 CLI 中可读。
- 不依赖 Codex 专有的 `agents/openai.yaml` 作为唯一入口；它可以存在，但只是 Codex UI 元数据。
- 若某个 CLI 需要额外入口文件，只创建薄适配层，指向同一份 `SKILL.md` 和 `references/`。

建议交付形态：

```text
lark-card-designer/
  SKILL.md
  references/
    ...
  agents/
    openai.yaml        # Codex UI metadata, optional for other CLIs
```

后续可选适配：

- Codex：原生使用 `SKILL.md`，保留 `agents/openai.yaml`。
- Claude Code：优先复用 `SKILL.md` 和 `references/`；如目标环境需要特定安装位置或入口，仅写轻量适配说明。
- OpenCode：优先复用 `SKILL.md` 和 `references/`；如需要命令/agent 配置，创建薄包装，不复制核心内容。

边界：

- 本 skill 不是多 CLI 安装器。
- 本 skill 不承担为每个 CLI 写完整插件。
- 本 skill 的核心可移植性来自 Markdown 规范、清晰触发描述、相对路径 references 和无专有工具依赖。

### 2.20 样例放置方式

已确认：

- 每类场景一个最小样例，放在 `references/examples.md`。

设计含义：

- `examples.md` 默认不强制加载。
- 当用户要求示例、样例输出、同场景对比，或 Codex/Claude/OpenCode 需要参考具体格式时再读取。
- 样例文件使用普通 Markdown，不依赖 CLI 专有语法。
- 每个样例应保持短小，重点展示设计判断和结构化决策块，不展示完整可发送 JSON。

### 2.21 跨 CLI 入口适配策略

已确认：

- 通用 skill 核心 + 轻量适配入口。

设计含义：

- 核心内容仍只维护一份：`SKILL.md` + `references/`。
- 可增加 `adapters/` 或等效薄入口文件，帮助 Claude Code、OpenCode 等 CLI 找到并使用主 skill。
- 适配层只能指向主 `SKILL.md` 和 `references/`，不能复制核心规则。
- 适配层不承诺完整插件实现、不包含安装器、不包含独立命令逻辑。
- Codex 的 `agents/openai.yaml` 仍可存在，但只作为 Codex UI 元数据。

## 3. 非目标

`lark-card-designer` 不应成为：

- 飞书卡片 SDK
- webhook 发送工具
- 卡片模板市场
- 所有业务场景的完整 BI 系统
- 自动美化任意文本的 formatter
- 只依赖 prompt 的“卡片生成助手”

这些能力可以由下游工具或其他 skill 承担，本 skill 只负责设计判断与结构建议。

## 4. 输入模型

Skill 应尽量识别以下输入维度。

### 4.1 数据类型

- 标量 KPI：销售额、完成率、库存数、审批金额
- 时间序列：日报、周报、环比、同比、趋势
- 明细表：商品列表、SKU、商机列表、审批记录
- Top-N 榜单：热度榜、销售排行、异常排行
- 文档/文章：blog、资讯、研究资料
- 流程对象：审批单、发版单、任务单
- 告警/状态：异常、风险、失败、恢复、待处理
- 富媒体：图片、链接、文件、人员 mention

### 4.2 数据意图

- 汇报：让读者快速知道结果
- 诊断：解释为什么变化
- 决策：让读者做批准、拒绝、选择
- 执行：让读者知道下一步动作
- 预警：提示风险或异常
- 沉淀：形成知识、资料、摘要
- 追踪：展示状态、进度、历史

### 4.3 输出口径

- 管理层：结论、风险、决策点
- 业务运营：指标、趋势、异常、待办
- 一线执行：对象、动作、截止时间、按钮
- 复盘分析：结论、证据、原因、改进
- 知识/资讯：主题、摘要、来源、优先级、反馈

### 4.4 约束条件

- 卡片是否需要交互
- 是否需要审批/确认
- 是否有图表需求
- 是否有明细表格
- 是否需要移动端阅读
- 是否需要多语言
- 是否需要长内容拆分
- 是否需要保留来源/审计/数据更新时间

## 5. 输出模型

建议 skill 的稳定输出包括 8 个段落。

### 5.1 `card_intent`

说明识别到的数据类型、数据意图、输出口径。

### 5.2 `card_pattern`

推荐卡片模式，例如：

- Executive summary card
- Ops dashboard card
- Action/approval card
- Analysis card
- Digest card
- Alert card
- Progress card

### 5.3 `information_architecture`

说明首屏、正文、明细、footer/note 的层级。

### 5.4 `component_plan`

列出建议组件和使用原因：

- header
- markdown/div
- table
- chart
- column_set
- collapsible panel
- button/action
- select/input/form
- image
- note/footer

### 5.5 `visual_rules`

说明状态色、标签、强调、密度、分隔规则。

### 5.6 `interaction_rules`

说明按钮、审批、反馈、刷新、锁定态、二次确认等规则。

### 5.7 `json_skeleton`

只提供骨架示意，不直接承担完整实现。

### 5.8 `validation_checklist`

检查是否存在：

- 首屏过载
- 表格过大
- 状态色无语义
- 行动不明确
- 指标无单位/周期
- 数据来源缺失
- 审批缺少审计字段
- 资讯缺少来源和优先级

## 6. 典型场景需求

### 6.1 日报/周报

目标：

- 让读者快速知道整体状态、关键变化、异常风险、下一步动作。

推荐结构：

1. 周期和总体状态
2. 关键结论
3. 关键 KPI
4. 重点变化
5. 风险/异常
6. 行动项
7. 明细折叠或表格

需要明确：

- 日报/周报是否更偏管理汇报，还是业务执行追踪。
- 是否需要固定 KPI 集合。
- 是否要求输出行动项 owner。

### 6.2 商品数据

目标：

- 帮助读者理解商品表现、库存风险、转化问题、Top/Bottom 商品。

推荐结构：

1. 商品/类目/店铺和周期
2. 销售、库存、转化、退款等 KPI
3. 异常标签
4. Top-N 和 Bottom-N
5. SKU 明细表
6. 商品图片或链接

需要明确：

- 商品数据更偏电商运营、库存管理，还是销售汇报。
- 是否需要图片占位。
- 商品明细字段优先级。

### 6.3 销售数据

目标：

- 展示目标达成、趋势、漏斗、区域/渠道/团队差异和行动建议。

推荐结构：

1. 周期和销售范围
2. 达成率和预测缺口
3. 趋势/同比/环比
4. 漏斗或渠道拆解
5. Top/Bottom
6. 待跟进动作

需要明确：

- 销售数据以 CRM 商机为主，还是订单/收入结果为主。
- 是否需要预测、目标、同比/环比。
- 是否需要按角色切换口径。

### 6.4 前沿 blog / 文章汇总

目标：

- 帮助读者判断哪些内容重要、为什么重要、是否需要阅读或跟进。

推荐结构：

1. 主题和时间范围
2. 必读/可选/存档分类
3. 每条内容标题、摘要、来源、标签、链接
4. 重要性说明
5. 反馈按钮

需要明确：

- 是否需要个性化偏好反馈。
- 是否需要按主题聚类。
- 摘要长度和条目数量上限。

### 6.5 审批卡片

目标：

- 让审批人清楚对象、原因、风险、影响和可执行动作。

推荐结构：

1. 审批对象和状态
2. 申请人、时间、类型
3. 审批内容
4. 风险/影响范围
5. 同意、拒绝、退回、查看详情
6. 审批后锁定态
7. 审计记录

需要明确：

- 审批类型范围：费用、发版、采购、内容、权限，还是通用审批。
- 是否只做样式建议，还是需要描述按钮状态机。
- 是否需要审批前后二态/多态。

### 6.6 复盘分析

目标：

- 从结果、事实、原因、影响和改进动作中形成可追溯分析。

推荐结构：

1. 主题和结果状态
2. 一句话结论
3. 事实和指标
4. 对比基准
5. 原因分析
6. 改进行动
7. 附录/明细折叠

需要明确：

- 是否采用固定复盘框架，如 What/Why/Next。
- 是否需要强制输出证据链。
- 是否需要行动项表格。

## 8. 关键风险

### 8.1 输出太像 prompt

风险：skill 最终变成“你要这样提示模型”的模板集，仍然会漂移。

控制方式：

- 主输出使用结构化段落。
- prompt 只作为可选附录，不作为主产物。
- 用明确的组件选择理由和检查表约束。

### 8.2 过早变成卡片生成器

风险：开始维护完整 JSON 和 API 细节，偏离设计决策层。

控制方式：

- JSON 只给骨架。
- 官方 API 细节放 constraints，按需读取。
- 不实现发送、更新、回调代码。

### 8.3 场景过多导致规则泛化

风险：每个场景都只说一点，最终不可执行。

控制方式：

- 先做 6 个高优先级模式：日报周报、商品、销售、资讯汇总、审批、复盘。
- 其他场景先归类，不单独展开。

### 8.4 口径之间差异不明显

风险：管理层、运营、一线、分析、知识口径输出长得差不多。

控制方式：

- 每个口径定义首屏重点、禁忌、组件偏好。
- 同一数据样例要能输出不同口径的设计差异。

## 9. 待确认需求

按轮询方式，建议分批确认。

### 第 1 轮：输出物边界

需要确认 skill 每次被调用时，默认输出到什么详细程度。

候选：

- A. 轻量决策：只输出卡片模式、信息架构、组件建议。
- B. 标准设计稿：输出决策、信息架构、组件、视觉、交互、JSON 骨架、检查表。
- C. 深度规范：再额外输出字段映射、异常分支、多口径差异和可测试样例。

初步建议：默认使用 B。它足够稳定，也不会变成完整卡片生成器。

### 第 2 轮：是否需要示例样本

需要确认是否为每类场景准备一个最小样例。

候选：

- 日报/周报样例
- 商品数据样例
- 销售数据样例
- 文章汇总样例
- 审批样例
- 复盘样例

初步建议：需要。skill 的稳定性会明显依赖示例，但示例应放 references，不塞进 `SKILL.md`。

已确认：选择 B，每类一个最小样例。

### 第 3 轮：JSON 骨架边界

需要确认 JSON 骨架是否贴近飞书 JSON 2.0。

候选：

- 只给伪结构
- 给接近 JSON 2.0 的骨架，但不保证可直接发送
- 给完整可发送 JSON

初步建议：第二种。足够指导实现，同时不偏离 skill 定位。

已确认：选择 B，给接近飞书 JSON 2.0 的骨架，但不保证可直接发送。

### 第 4 轮：图表能力边界

需要确认图表是否作为规范重点。

候选：

- 仅说明何时应该用图表
- 进一步说明趋势、占比、漏斗、排行分别适合什么图表
- 提供图表 JSON 示例

初步建议：第二种。

已确认：选择 B，说明趋势、占比、漏斗、排行分别适合什么图表。

### 第 5 轮：审批/交互深度

需要确认审批卡片是否只提供样式结构，还是提供状态机建议。

候选：

- 只做结构：展示字段和按钮
- 做状态机：待审批、已同意、已拒绝、已退回、已过期
- 做权限规则：审批人、代理人、RBAC、审计

初步建议：做状态机，不做权限系统。

已确认：选择 B，做审批/交互状态机建议，不做权限/RBAC 实现。

### 第 6 轮：口径缺省处理

需要确认当用户没有明确说明输出口径时，skill 应该如何处理。

候选：

- A. 必须追问口径：最稳，但会打断使用流。
- B. 主动推断并标注假设：默认选择最可能口径，必要时给出 1 到 2 个替代口径。
- C. 同时输出多口径差异：最完整，但每次输出更长。

初步建议：选择 B。它能保持协作流畅，也能通过“假设声明 + 替代口径”降低误判风险。

已确认：选择 A+B 混合策略。默认主动推断并标注假设；当口径会显著影响结构或信息不足时，先追问一个关键问题。

### 第 7 轮：输出格式结构化程度

需要确认 skill 的最终回答格式更偏自然语言还是机器可解析结构。

候选：

- A. Markdown 分段：阅读舒服，适合人工看，但结构稳定性稍弱。
- B. Markdown + 结构化决策块：先给简短说明，再给固定字段块，推荐。
- C. 纯 JSON/YAML：最稳定，但读起来像配置文件，不利于设计解释。

初步建议：选择 B。它既能给人读懂设计理由，又能让下游实现者稳定提取 `card_intent`、`card_pattern`、`component_plan`、`json_skeleton` 等字段。

已确认：选择 B，使用 Markdown + 结构化决策块。

补充确认：主触发场景是开发过程中涉及飞书卡片设计时调用本 skill，而不是直接把 skill 定义成最终卡片生成器。

### 第 8 轮：已有卡片评审/优化范围

需要确认 skill 除了设计新卡片，是否也负责评审和优化已有卡片。

候选：

- A. 只设计新卡片：边界最窄。
- B. 设计新卡片 + 评审/优化已有卡片：推荐，贴合开发场景。
- C. 设计 + 评审 + 迁移旧 JSON 到新结构：范围最广，可能接近实现工具。

初步建议：选择 B。开发时经常会遇到已有卡片不好读、组件选择不合适、口径不清的问题，评审能力会很实用；但迁移旧 JSON 可暂时不纳入 MVP。

已确认：选择 B，覆盖设计新卡片和评审/优化已有卡片，不默认做旧 JSON 迁移。

### 第 9 轮：开发实现参与边界

需要确认当开发任务正在实现飞书卡片时，本 skill 应参与到什么程度。

候选：

- A. 只输出设计决策：不看代码、不改代码，只给设计方案。
- B. 输出设计决策 + 指导/评审实现：可读代码或 JSON，指出实现是否符合设计，但不默认直接改代码，推荐。
- C. 输出设计决策 + 直接参与实现：必要时修改代码、JSON、模板，更像开发型 skill。

初步建议：选择 B。它符合“主要用途是指导不同输出口径的卡片样式”，又能适配开发过程中的实际使用，不会把 skill 变成卡片生成器或 API 工具。

已确认：选择 A + 指导/评审。角色是设计师，可以指导和评审实现，但不参与代码、JSON、模板修改。

### 第 10 轮：飞书能力基准

需要确认设计规范默认以哪一代飞书卡片能力为基准。

候选：

- A. JSON 2.0 为主：默认按飞书卡片 JSON 2.0 组件能力做设计，最适合 MVP。
- B. JSON 2.0 + CardKit 概念参考：设计层以 JSON 2.0 为主，同时参考 CardKit 的卡片实体、局部更新、模板管理能力。
- C. JSON 1.0 / JSON 2.0 / CardKit 全兼容：覆盖最广，但规范会更重。

初步建议：选择 B。它不把 skill 做成实现工具，但能让设计建议理解新版卡片能力和局部更新/模板化思路。

已确认：选择 B，JSON 2.0 为主，CardKit 概念作为局部更新、模板化、卡片实体生命周期参考。

### 第 11 轮：视觉风格边界

需要确认 skill 默认给出的视觉风格应该多强。

候选：

- A. 飞书原生克制风格：主要依赖信息层级、状态色、组件选择，不做强装饰。
- B. 语义状态优先 + 可配置品牌轻定制：默认克制，但允许根据品牌/业务场景给 header、标签、图片、强调色建议，推荐。
- C. 强视觉主题化：每类卡片都设计明显风格，如小红书风、运营大屏风、报告风，表达强但容易漂移。

初步建议：选择 B。它符合卡片设计师角色，也能避免所有卡片变成同一种“好看但不清楚”的风格。

已确认：选择轻量 B。默认语义状态优先，认可强调色建议，但不需要复杂品牌定制选型或强主题化。

### 第 12 轮：质量验收严格度

需要确认 skill 在输出设计方案或评审已有卡片时，质量检查做到什么程度。

候选：

- A. 基础检查：只检查首屏是否清楚、组件是否合适、状态色是否有语义。
- B. 设计红线 + 改进建议：检查首屏、层级、组件、交互、状态、数据来源、移动端可读性，并给出修改方向，推荐。
- C. 评分量表：按信息清晰度、交互完整性、视觉一致性、飞书约束等打分，最严格但更重。

初步建议：选择 B。它符合“设计师评审”的角色，不会变成繁琐审计。

已确认：选择 B，采用设计红线 + 改进建议，不默认使用评分量表。

### 第 13 轮：MVP reference 范围

需要确认首版 skill 的 references 应该做到什么粒度。

候选：

- A. 极简 3 文件：`decision-matrix.md`、`card-patterns.md`、`component-rules.md`。
- B. 标准 6 文件：再加入 `audience-portfolios.md`、`visual-status-rules.md`、`rendering-constraints.md`，推荐。
- C. 完整 7+ 文件：再加入 `examples.md` 或按场景拆分多个 examples 文件。

初步建议：选择 B。样例可以先合并在 `card-patterns.md` 或单独轻量附录，避免首版 reference 过散。

已确认：按标准 skill 交付。首版运行时资源采用 `SKILL.md` + `agents/openai.yaml` + `references/`；`docs/` 只作为调研和原始资料留存。

补充确认：交付物需要尽量兼容 Codex、Claude Code、OpenCode 等 coding CLI。核心内容采用通用 `SKILL.md` + `references/`，Codex 的 `agents/openai.yaml` 仅作为 UI 元数据，不作为唯一入口。

### 第 14 轮：样例放置方式

已确认每类场景需要一个最小样例。现在需要确认样例放在哪里。

候选：

- A. 合并在 `card-patterns.md`：文件少，引用方便，但卡片模式文件会变长。
- B. 单独 `examples.md`：结构清晰，默认不加载样例，推荐。
- C. 按场景拆分多个 example 文件：最清楚，但首版文件偏多。

初步建议：选择 B。`SKILL.md` 可以在需要示例时再让 Codex 读取 `references/examples.md`，符合渐进加载。

已确认：选择 B，样例单独放在 `references/examples.md`。

### 第 15 轮：跨 CLI 入口适配策略

需要确认为了让 Codex、Claude Code、OpenCode 都能用，首版是否要包含适配入口。

候选：

- A. 只交付通用 skill 核心：`SKILL.md` + `references/`，由各 CLI 用户自行引用。
- B. 通用 skill 核心 + 轻量适配说明/薄入口：核心仍只维护一份，必要时增加 CLI 入口指向 `SKILL.md`，推荐。
- C. 为每个 CLI 单独维护一套配置和命令：上手最直接，但维护成本高且容易漂移。

初步建议：选择 B。它能满足跨 CLI 使用，同时守住“核心内容只维护一份”。

已确认：选择 B，交付通用核心，并提供轻量适配入口；适配层只做指针，不复制核心规则。

### 第 16 轮：是否进入 skill 实施

当前需求已经足够支撑首版标准 skill。

候选：

- A. 继续轮询更多细节。
- B. 开始实施首版 skill：创建 `SKILL.md`、`agents/openai.yaml`、`references/` 和轻量 `adapters/`。
- C. 先输出实施计划，不创建文件。

初步建议：选择 B。继续轮询的边际收益已经开始下降，先做出首版，再通过真实样例迭代会更有效。

已确认：选择 B，开始实施首版 skill，创建 `SKILL.md`、`agents/openai.yaml`、`references/` 和轻量 `adapters/`。
