# Code2Lark 项目概览

## 项目名称

**Code2Lark**

## 项目介绍

Code2Lark 是一个面向产品和工程团队的飞书 / Lark 接入交付工具。它把已有业务能力或正在建设中的新能力，整理成可审查、可验证、可交接的 Lark 入口，让团队可以通过飞书卡片、机器人动作或内部工作流使用目标服务。

Code2Lark 支持两条核心路径：**Retrofit** 面向已有项目接入，**Co-Build** 面向新能力与 Lark 入口同步建设。当前默认交付形态是目标项目内的隔离模块：

```text
integrations/lark
```

该模块采用 embedded-long-connection 长连接方式，真实联调时用户只需补充 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、操作员白名单，并在飞书后台配置机器人能力、长连接、`card.action.trigger`、权限和测试群。

## 核心功能

- **Retrofit 已有能力接入**：为已有服务、API、任务或内部工具补充 Lark 访问入口。
- **Co-Build 新能力共建**：从 0 或半成品阶段开始，帮助定义业务契约、Lark 卡片入口、确认流程和验证方式。
- **能力映射与风险识别**：把项目接口、任务或函数整理为 capability map，标注输入、输出、风险、确认要求和不确定点。
- **Lark 卡片动作设计**：支持预览、确认、运行中、成功、失败、已完成等状态流。
- **安全执行边界**：内置 prepare/confirm、操作员白名单、幂等、防重复点击、过期预览拦截和审计字段设计。
- **隔离模块交付**：默认交付 `integrations/lark`，不接管业务代码、根启动脚本、Docker 或生产部署。
- **验证与交接**：生成本地验证、模拟动作、诊断、README、`.env.example`、Level 2 证据模板和交接说明。

## 解决的痛点

- 把业务接口接入飞书时，常常需要手工理解代码、设计卡片、写回调、补权限、做验证和整理交接，过程分散且容易遗漏。
- 风险动作如果直接做成按钮，容易出现误触、重复执行、越权执行或无法追踪的问题。
- 业务团队、飞书应用 owner、开发者和测试人员之间经常缺少统一的契约和证据材料。
- 新功能开发时，Lark 入口常被放到最后补，导致接口形态、安全边界和交互体验反复返工。
- 真实飞书联调前，环境变量、权限、事件订阅、测试群和证据要求不清晰，排障成本高。

## 应用场景

- 内部运营任务：周报、销售简报、库存补货、数据同步、批量处理。
- 管理后台轻量入口：状态查看、刷新、审批、启动或停止任务。
- 风险操作前置确认：发布、通知、外部发送、数据变更、停止任务。
- 已有 Web/API 服务接入 Lark：不改变原服务生命周期，增加团队协作入口。
- 新内部工具共建：业务能力和飞书卡片入口一起设计，减少后期返工。
- 多团队交接：把配置、权限、验证、剩余人工步骤和证据模板标准化。

## 通用能力

- **结构化能力发现**：基于内置分析器、profile 规则和人工可审查的 capability map 输出候选能力。CodeGraph 可作为未来增强方向，但不是当前交付依赖。
- **业务契约抽象**：优先用 `status`、`dry-run`、`execute`、`cancel/stop` 描述目标能力，明确哪些由业务系统负责，哪些由 Code2Lark 负责。
- **卡片交互模型**：将业务操作转化为候选、预演、确认、执行、结果和失败恢复等用户可理解的卡片流程。
- **安全与审计模型**：默认把有副作用的动作放入确认链路，记录 operator、chat、action、confirmation id、trace id 和结果。
- **长连接交付模型**：当前默认使用 embedded-long-connection，不把 `PUBLIC_CALLBACK_BASE_URL`、`VERIFICATION_TOKEN` 或 `/webhook/card` 作为纯长连接路径的默认要求。
- **本地验证闭环**：在真实飞书凭据准备好之前，先通过本地测试、模拟 payload、strict verify 和 doctor 检查减少联调风险。

## 核心价值提升

- **从“写一个飞书入口”提升为“交付一个可审查的业务入口契约”**：让产品、业务和工程能先确认能力边界，再接入 Lark。
- **从“按钮直连接口”提升为“安全确认工作流”**：降低误触、重复执行、越权和不可追踪风险。
- **从“一次性 demo”提升为“Level 2-ready 交付”**：交付物包含配置模板、验证命令、证据模板和剩余人工步骤。
- **从“散落脚本和说明”提升为“隔离模块”**：默认沉淀到 `integrations/lark`，便于审查、测试、移交和后续维护。
- **从“事后补 Lark”提升为“双路径交付”**：已有能力可以 Retrofit 接入，新能力可以 Co-Build 同步设计，减少返工。

## 效率提升预期

以下是常见内部工具、API、任务型项目的经验估算，实际耗时取决于项目复杂度、业务契约清晰度、飞书权限审批和真实联调环境。

| 工作内容 | 传统人工方式 | Agent + Code2Lark 后 | 主要节省 |
|---|---:|---:|---|
| 能力盘点与接入范围确认 | 4～16 小时 | 0.5～2 小时 | 自动整理候选能力、风险和待确认问题 |
| 卡片交互与确认流程设计 | 4～16 小时 | 1～3 小时 | 复用预览、确认、运行中、成功、失败等状态模型 |
| Lark 接入代码与模块骨架 | 8～24 小时 | 1～4 小时 | 自动生成隔离模块、配置模板、动作处理和验证脚本 |
| 安全边界与异常场景补齐 | 4～16 小时 | 1～3 小时 | 内置白名单、幂等、防重复点击、过期预览和审计规则 |
| 本地验证与交接材料 | 4～12 小时 | 0.5～2 小时 | 自动生成验证命令、报告、README 和 Level 2 证据模板 |

整体来看，简单到中等复杂度的 Lark 接入，原先通常需要 **24～64 小时** 的跨角色协作；通过 Agent 调用 Code2Lark 自动化后，常见可压缩到 **4～12 小时** 完成本地可验证交付，约节省 **60%～85%** 的准备、实现和交接时间。真实飞书权限审批、租户配置和生产发布仍需人工完成，不计入自动化节省承诺。

## 后续迭代方向

- 覆盖更多项目类型与技术框架，提升不同业务形态下的接入适配能力。
- 强化能力发现、语义理解与风险识别，减少人工梳理和确认成本。
- 将 CodeGraph 作为可选增强能力，在需要时补充更丰富的代码结构上下文，而不是当前交付依赖。
- 丰富生成的 `integrations/lark` 模块模板，覆盖更多宿主形态、交互流程和业务操作模式。
- 提升 Level 2 证据的自动采集、整理与校验能力，缩短从本地验证到真实联调的距离。
- 沉淀更可复用的验证、诊断、交接和 handoff 工作流，帮助团队稳定交付 Lark 接入包，同时保持业务系统和生产部署边界清晰。
