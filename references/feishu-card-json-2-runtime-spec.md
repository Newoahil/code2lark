# Feishu/Lark Card JSON 2.0 Runtime Spec

This reference is the Code2Lark runtime boundary for Feishu/Lark Card JSON 2.0. It does not replace `embedded-skills/lark-card-designer/SKILL.md`.

Use `lark-card-designer` for card information architecture, visual hierarchy, state design, and interaction intent. Use this spec only when converting that design handoff into production-sendable runtime payloads, sender payloads, callback responses, and verifier checks.

In the current skill package, this spec is primarily a Co-Build delivery gate for generated `integrations/lark` modules. Retrofit should follow the same boundary when it converts existing or newly designed cards, but this small iteration is optimized for Co-Build handoff reliability.

## 1. Ownership Boundary

```text
lark-card-designer design sketch
  -> Code2Lark runtime adapter
  -> Feishu/Lark Card JSON 2.0 runtime payload
  -> verify:card or equivalent local verifier
  -> real Feishu/Lark sender and card.action.trigger runtime
```

- Lark Card Designer output is a design handoff or JSON 2.0-like sketch, not a production payload.
- Code2Lark must not reinterpret Lark Card Designer visual rules. It should preserve the approved intent while mapping it to supported runtime components.
- Production sends and callback card updates must use runtime payloads generated by the Code2Lark adapter, not copied Lark Card Designer sketches.

## 2. Runtime Card Shape

Every production card JSON used for message sends or callback card updates must use this baseline shape:

```json
{
  "schema": "2.0",
  "header": {
    "title": {
      "tag": "plain_text",
      "content": "Card title"
    }
  },
  "body": {
    "elements": []
  }
}
```

Required runtime checks:

- `schema` is exactly `"2.0"`.
- `header.title` exists.
- `body.elements` exists and is an array.
- Design-only fields are absent from the runtime card, including `json_2_0_like`, root-level `elements`, root-level `note`, `sketch`, `metadata`, and other adapter-only annotations.

## 3. Supported Runtime Subset

The runtime adapter should prefer a conservative, verifiable subset until the target component has been tested in real Feishu/Lark:

- Text/content: `markdown`, `plain_text`, `div`.
- Layout: `column_set`, `column`, `hr` or other verified separators.
- Interactive: `button` with JSON 2.0 `behaviors`.
- Structured data: `table` only when the generated verifier and real tenant test cover it.
- Inputs/selectors only when the target business contract needs them and the callback parser preserves their values safely.

If a component is not in the local verifier's supported set, either add verifier coverage from official docs before using it or map the design intent to the supported subset.

## 4. Banned Runtime Tags and Fields

The verifier must recursively scan every tag-bearing node. Runtime payloads must reject at least:

- `tag: "action"` — this is a legacy action block and is not valid for the JSON 2.0 runtime path Code2Lark uses. Put buttons directly in `body.elements` or inside `column_set` / `column`.
- `tag: "note"` — this is a design/footer intent, not a runtime component in the supported subset. Map it to `markdown` or `div`.
- Buttons that use only legacy top-level `value`, `action_type`, or old callback shapes.
- Design-only fields such as `json_2_0_like`, root-level `elements`, root-level `note`, `sketch`, and `metadata`.

These failures are hard blockers for real sends and Level-2-ready Co-Build handoff.

## 5. Lark Card Designer Sketch to Runtime Mapping

Use these mappings when adapting Lark Card Designer output:

| Lark Card Designer / design intent | Runtime mapping |
|---|---|
| Main title | `header.title` |
| Body paragraph or explanation | `markdown` or `div` in `body.elements` |
| Warning, caveat, or footer note | `markdown` / `div` with restrained text and safe status wording |
| Multiple action area | `column_set` containing `column` elements, each containing a `button` |
| Primary/secondary/destructive action intent | `button` text/type plus callback `action` mapped to a known handler and safety gate |
| Running/success/failure state | Separate runtime card builder states returning JSON 2.0 cards |

Do not copy Lark Card Designer structural placeholders into production JSON. Treat them as instructions to the runtime adapter.

## 6. Button Callback Pattern

JSON 2.0 interactive buttons must use `behaviors`:

```json
{
  "tag": "button",
  "text": {
    "tag": "plain_text",
    "content": "Confirm"
  },
  "type": "primary",
  "behaviors": [
    {
      "type": "callback",
      "value": {
        "action": "business.operation.confirm",
        "confirmation_id": "server-held-or-bound-id"
      }
    }
  ]
}
```

Required checks:

- Every callback button has `behaviors[].type === "callback"`.
- `behaviors[].value.action` exists.
- The action maps to a known generated handler.
- Risky actions still use host-local prepare/confirm, operator allowlist, idempotency, and stale/forged preview rejection.

## 7. Message Send Payload Shape

When sending an interactive card through Feishu/Lark message OpenAPI:

```json
{
  "receive_id": "configured-chat-id",
  "msg_type": "interactive",
  "content": "{...stringified card JSON...}"
}
```

Required checks:

- `msg_type` is `"interactive"`.
- `content` is `JSON.stringify(cardJson)`.
- Do not wrap the card as `{ "card": cardJson }` for message sends.
- Logs and evidence must not print real chat ids, open ids, message ids, app secrets, access tokens, or raw OpenAPI responses.
- The sender may use Feishu/Lark OpenAPI over HTTPS with Node built-in `fetch`; this is not a transport downgrade by itself because it only sends the card.
- Do not treat HTTPS send success as proof that `card.action.trigger` receive runtime is active.

## 8. `card.action.trigger` Callback Response Shape

For card action responses:

```json
{
  "toast": {
    "type": "info",
    "content": "Accepted"
  },
  "card": {
    "type": "raw",
    "data": {
      "schema": "2.0",
      "header": { "title": { "tag": "plain_text", "content": "Updated" } },
      "body": { "elements": [] }
    }
  }
}
```

- Returning only `toast` is allowed when no card update is needed.
- When updating or replacing a card, return `card: { type: "raw", data: cardJson }`.
- Do not return raw card JSON directly under `card`.
- Do not confuse callback response shape with OpenAPI message-send `content`.
- Receiving `card.action.trigger` must still use the selected runtime transport. If Co-Build selected embedded-long-connection, HTTP callback fallback requires explicit developer confirmation.

## 9. Co-Build Verifier Requirements

Every Co-Build `integrations/lark` delivery must include `verify:card` or an equivalent local verifier before real tenant testing. It must cover:

- OpenAPI send-message payload shape.
- Runtime card baseline shape.
- Recursive banned tag and design-only field scan.
- JSON 2.0 button `behaviors` callback pattern.
- Known-handler mapping for every callback action.
- Callback response card shape.
- Dependency/transport preflight: sender path, long-connection SDK dependency state, and no silent HTTP callback fallback.
- Sanitized diagnostics and no secret/id/raw callback leakage in output examples.

If a generated Co-Build demo bypasses this verifier, it is not Level-2-ready.
